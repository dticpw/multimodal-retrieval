# 复测报告 — 2026-04-23

**动机**：怀疑 2026-04-16 首轮报告的 9.2s p50 受冷启动污染（原报告仅 warmup=2），体感体验似乎更快。本次连续跑 3 轮、每轮 warmup=5 / measured=10，独立进程、无共享状态，用于排除冷启动干扰并验证 LLM 生成延迟的稳定性。

## 结论

1. **冷启动不是 E2E 9s 的原因**。首次 CLIP encode 冷启动 1.3–1.9s，稳态 37–40ms（加速比 34–48×），但 warmup=5 已完全吸收；稳态 p50 仍 ~8.9s，与 2026-04-16 的 9.2s 基本一致。
2. **瓶颈 100% 在 LLM 调用**。LLM Generate p50 均值 8,719 ms，占 E2E 的 98.0%；Query Rewrite 再占 6.7%；CLIP + FAISS + SQLite 合计 < 50 ms，不到 E2E 的 0.5%。
3. **体感 < 9s 的来源**：非 RAG 路径（纯检索 /api/v1/search/text）本地端到端 ~40ms，与 RAG 路径的 8.9s 不是同一链路。若以体感校准 RAG 路径，需引入流式输出——首 token 时延（TTFT）通常只有 200–500ms，可让用户在 LLM 仍在生成时就看到内容，主观体验显著优于等完整响应。
4. **下一步优化方向**（与首轮报告一致）：
   - 流式 SSE 输出，把感知延迟从 9s 压到亚秒级 TTFT
   - 对重复/相似 query 做语义缓存
   - 评估换更快的 LLM 端点或直连，当前中转链路 LLM 本身贡献近 90%
